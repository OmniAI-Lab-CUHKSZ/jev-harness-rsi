# AppWorld 公共工具版 Jev harness 执行与复现手册

本文对应 `appworld_native_tools_v2` 的正式入口 `native-run` 和 Train 小样本入口 `native-pilot`。实验首先检验固定的 27B 通过选择官方工具、对象与参数能完成哪些任务，再检验 Sol 从 Train 轨迹提炼的共享改动能否提高后续整题成功率并减少在线输出。每道题都有自己独立的 AppWorld 世界。任务之间传递的是公共 harness，账号会话、工具回显、对象 ID 和上道题的环境状态都随任务结束。

组合卡片版通过 `native-pilot --composed` 运行。读取计划检查、卡片输出字段映射及四题复测库见[组合版复现说明](reproduce.md#composed-card-pilot)。

## 正式实验的启动顺序和选版

`python -m jev_harness native-plan` 在本地打印完整的任务 ID、初始库与预算。从新目录启动 `native-run`，可用 `--through react-dev`、`--through h0-dev`、`--through train`、`--through test` 分段执行。同一目录续跑会复用逐题记录。命令接受 `--connections` 与 `--root`，默认最多 6 张 A800、每卡两条独立环境、从头启用 CUDA Graph。

1. 全生成 ReAct 先跑完 Dev 的 57 题。27B 每步生成一项结构化官方工具调用、计算或检索，程序执行并返回观测。新 H0 再独立跑同一 57 题，优先使用程序生成的菜单，交给 Jev 选择。两者共享模型、工具目录、认证、分页和计分器。H0 保留内置的字段投影、通用计算及 Markdown 清单绑定等已开发的公共能力，六组可学习对象全部重新置空。历史 pilot 学到的片段、修改和轨迹不导入正式运行。第二次 Dev 建立批次选版的父版逐题记录。
2. 按清单顺序处理 10 批 Train，每批 3 个场景、9 道题。每道题只用批次入口 harness 采样一次，第一批用 H0，后续批次用上一批经 Dev 保留的版本。Sol 从这 9 条轨迹中的菜单、Jev 选择或弃权、局部生成请求、工具返回与真实写入定位错误，并挖掘可替换生成的操作。已完成批次的 harness 轨迹可通过索引按需展开。十批共采集 90 条入口轨迹，候选整批重跑、草案试跑和条件复测分别计数。全生成 ReAct 只参加正式实验开头的 Dev 对照和最后的 Test-Normal 对照。Sol 的证据来自 Train。
3. 每轮 Sol 可改至多 3 个具名对象。草案在全部 9 道父版 Train 的已记录路径上检查首处变化，其中至多一个变动菜单请真实 27B 重选；至多一道受影响的当前题另开环境实跑草案。对以前批次曾在判断臂做对的每道 Train，检查最近一条成功路径，每题只查首变，每轮最多 24 个历史菜单真实复选。更多待复选、变化的生成或工具请求分别列出。菜单一致只能说明当前前缀一致。草案、审阅和最终提案分开保存。审阅再修改时，历史复选报告绑定原草案，`final_matches_draft` 标记二者是否相同。
4. 有实际改动的最终候选重新跑本批全部 9 题，和本轮父版比较。成功数优先，相同才比较在线输出 token，两者相同保留新版本。第一轮接受则第二轮从它开始，第一轮拒绝或未改动则从该轮父版开始。第二轮始终安排。它可读第一轮比较两侧的完整 Train 轨迹、逐题初测成败和 token，以及最终选版分数。草案整题预览的分数单独列账。
5. 批末有留存的 Train 新版本时，在 57 道 Dev 上与本批入口父版作一次比较。父版沿用本次实验该版本已测的逐题初测，候选新跑全板；涉及条件复测的题，父、子都重跑。通过则带入下一批，退步则恢复入口版本。没有留存新版本的批次直接沿用原 Dev 记录。
6. Train 和 Dev 共用条件配对复测。同输入分歧造成的翻转可能左右成功数胜负时，复测比较中的全部翻转题。成功数持平且同输入分歧题的成本贡献能改变节省量的符号时，复测相关成本题。复测题用同卡、同种子、独立世界，两次配对交换先后，每臂取两个复测均值，其余题保留初测。对新工具执行器，识别同输入分歧也检查此前的实际 API 入参、返回、观测及写入效果。
7. 第十批结束后关闭 Sol，最终保留版和全生成 ReAct 在 Test-Normal 的 30 个不同场景、90 题上作一次配对评测。报告整题通过率、场景三题全对率、生成与判断的输出成本、零开放生成题数、API 次数以及按场景重采样的差值区间。Sol、草案实跑、复选及条件复测有独立成本记录。

`versions/` 保存初始库和各轮候选，`runs/` 保存独立任务和原始轨迹，`offline/bXXrYY/` 保存 Sol 的提示、回复、草案和最终补丁，`batches/` 保存每次 Train/Dev 比较，`checkpoints.json` 保存实际继承关系。下文第 10、11 节的分数来自有历史入口片段的早期 Train 小实验，其首页当时仍会补足可用片段。正式冷启动的分数应从本次运行的 `initial_dev.json` 和 `test_report.json` 读取。

## 1. 从哪里开始复现

复现包解压后，项目根目录包含 `pyproject.toml`。以下为 bash 命令。Windows PowerShell 可以在一行输入同一条 CLI 命令，环境变量用 `$env:变量名` 设置。CPU 测试只需要 Python 3.10 以上与 pytest。真实推理还需要模型 worker、环境 worker。重新演化还需要已登录且可用 GPT-6.2 Sol Max 的 Codex 账号。

```bash
python -m pip install -e ".[test]"
python -m pytest -q
python -m jev_harness native-pilot --help
```

模型 worker 的参考环境为 Linux、A800 80 GB、BF16、Python 3.10、vLLM 0.31.0、Transformers 5.17.0。下载模型 `autotrust/AutoTrust-Decider-Pro-27B` 的 revision `14b425269ed24452e0a5ad5a8f3e51d139647a88`，包括官方 `serve_decide.py`、adapter 和校准数据。环境 worker 使用单独的 Python 3.12、AppWorld 源版本 `42b5bcf3cd334fee33f0c37c02070a9f5807add5` 与 data 0.2.0。逐条安装命令见同目录 [环境安装说明](reproduce.md)。单机用 `configs/connections.local.example.json`，设置 `APPWORLD_PYTHON`、`APPWORLD_ROOT`、`JEV_MODEL_PYTHON`、`JEV_MODEL_DIR`。跨机用 `configs/connections.ssh.example.json`，按模板填各端能访问的路径及 SSH 配置。脚本中的 `CONN` 指这一份连接文件。

```bash
CONN=configs/connections.local.example.json
TRAIN="29caf6f_1 cf6abd2_1 07b42fd_1"
CHECK="cf6abd2_2 29caf6f_2 afc0fce_1"
# 从空学习库运行相同题板
python -m jev_harness native-pilot --connections "$CONN" --root runs/v2-evolve \
  --train $TRAIN --check $CHECK --max-gpus 2
# 独立重测本地运行所得的两套库
python -m jev_harness native-pilot --connections "$CONN" --root runs/v2-score --phase score \
  --train $TRAIN --check $CHECK --entry-library runs/v2-evolve/entry_harness.json \
  --candidate-library runs/v2-evolve/offline/candidate.json --max-gpus 2
```

上述命令从空学习库起步。下文的历史试跑从更早的候选继续。要沿用自己的早期小试，可以添加 `--history-run` 并指向该次运行目录，同时使用新的 `--root`。指定设备可以把 `--max-gpus 2` 换成 `--gpus local:0,local:1`，多机时把 `local` 换成连接表中的节点名。自动分配看 A800、空闲显存至少 58,000 MiB、使用率至多 30%。每张卡装一份模型、共享两个并行推理会话，每条会话有独立的 AppWorld。CUDA Graph 使用 `FULL_DECODE_ONLY`，捕获 batch size 1 和 2。程序尽量把同一道题的各执行臂放在同一张卡。

可以把演化命令拆成 `--phase initial`、`--phase revise`、`--phase evaluate` 三次运行，使用相同根目录、题单和历史参数。保留运行目录可以续跑，已经保存的整题记录与已保存的候选会被复用。需要独立重复时换根目录。固定库重测用 `score`。温度、种子、模型与并发相同仍可能得到不同的输出，比较时记录每条实际轨迹。复现已知候选比重新调用 Sol 更适合检查同一补丁的表现。

历史输入 `native04` 开放过 `60d0b5b_1`、`07b42fd_1`、`29caf6f_1` 三道优化 Train。本轮前两类检查是新实例，第三类的场景不在当前或所开放的旧优化题中。清单第一题用于开发过本次修复，应按诊断题读数。本次三组共十八次正式计分，另计优化器内部的预览。这里的留出是 Train 内留出。只有正式盲评才能回答跨整套 Dev/Test 的泛化问题。

| 计分臂 | 模型每步的工作 | 读取哪份库 |
|---|---|---|
| `h0_generation` | 27B 生成一个结构化动作 | 空学习库，共享公共执行器、数据源、认证、分页与参数校验 |
| `h0_decision` | 优先 Jev 判断，可局部生成并重新进入判断 | `entry_harness.json`。本轮从历史候选继续，目录名里的 H0 表示本轮入口 |
| `candidate` | 与入口同一执行器、同一模型 | `offline/candidate.json`，即 Sol 审阅后的完整公共库 |

任务结束后调用 AppWorld 官方 evaluator，整题所有断言通过记 1，否则记 0。执行中只读公开题面、模拟时钟、主管身份、API 文档与本次公开 API 响应。环境以 `load_ground_truth=False` 启动，仅在执行结束后的评分步骤装载 ground truth。Sol 接受优化 Train 的成败与轨迹。送入索引的 summary 只含成败、输出、耗时和执行错误等字段。检查题的轨迹与分数不进入本轮编辑。

主要指标为每臂成功题数、所有计分题在线 `output_tokens` 之和。成本分成 `open_output_tokens` 与 `decision_output_tokens`。前者含生成一个结构化动作时的推理与回答，后者是自适应判断的推理输出。快速选择仍有输入、打分与设备耗时。另报 `open_calls`、`native_ballots`、模型计数、API 数与墙钟耗时。失败题也进入成本合计。Sol 每次回复的输出、真实复选与整题草案预览另计，避免在计分臂里重复记账。对摘要任务比较实际答案，对写操作比较作用对象、提交字段、回复内容和官方评分，二者各保留原值。此入口输出比较表，一轮产生一个候选，没有自动晋级到下一正式批次的步骤。

## 3. 每一道题的执行循环

**初始化。** AppWorld 重置当前实例并返回公开题面、模拟时间、主管身份、应用说明和 `api_docs.function_calling()` 给出的函数签名。每个工具带 `app__operation` 名、说明、参数类型、必填项、默认值及取值限制。计数器、登录会话、读缓存、观测、写回执、错误反馈、已用片段与派生状态都从空开始。一次循环只选择一个工具或一项本地计算。对同一批已选对象，程序可以用一套参数映射执行多次官方调用。

**状态。** 每个新观测按产生顺序编为 `r1,r2,…`，保存来源、原始公开返回、范围与是否覆盖完整集合。给 27B 的常规视图含最近 6 个观测、每个观测按题面词重合选出的最多两条相关样本及第一行（去重）、每行最多约 650 字符以及首行最多 35 个字段路径。另有最近 6 份写回执、最近 2 条错误、当前检索词和已产生的派生证据。完整返回保存在本次任务内，程序可从全部数据计算，模型可用 `inspect` 分段读取长字段。观测标号与对象 ID 是两层不同的标识。

**第一道题选择下一步。** 程序从官方目录按题面和状态排名。在首轮先取前 8 个工具。这页无适用项时取第 9–16 个。每页还可带匹配的片段、通用计算、完成和发现入口。方法按下划线和单词切词、转小写、去停用词并简化英文复数。以下相交数量均指不同的词或字段。排序采用下式。

```text
5 × 题面与操作名交集
+ 3 × 题面与(操作名、说明、该工具检索提示)交集
+ 2 × 题面与公开参数名的词交集
+ 6 × 题面与工具检索提示交集
+ 7 × 应用名的词都在题面中
+15 × 当前发现查询与(操作名、说明、检索提示、应用名)交集
− 8 × 最近观测中缺少的必填 *_id 数
+ 4 × 起步时是读取工具
+ 3 × 已有历史且有文字匹配时，可由当前字段供应的必填参数数
−13 × 此来源已在本题观测中出现
```

可供字段由最近三个观测的第一行展开。分数降序，同分按完整工具名排序。读操作按公开动词 `show/search/get/list/check/find/retrieve/is/does` 及 `_exists` 识别。登录由程序管理，完成另列。选择“浏览其他操作”会让 Jev 选应用或浏览已有输入的片段。在一个应用内每页最多看 10 个工具。两页都弃权或浏览用尽后进入局部生成。所有菜单至多 15 个实选项，外加 `NONE`。每一页都是程序当场组装的。

**片段与通用计算。** 已安装的片段必须找到一个主来源和所有声明的辅助来源。对每组实际观测引用建立一个可执行选项。已试过的同片段、同输入组合不重复尝试。首页可以推荐 0、1 或 2 项。Sol 可在片段内写 `goal_terms`，每个短语表示一种适用目标的说法。词形规范化后，至少一个短语的词要全部出现在题面，且其中至少有一个实质词超出来源名和通用词。分数取匹配短语中这类实质词的最大数量。未声明短语的旧片段按题面与标签里实质词的交集数量计分。同分沿用可执行列表中的顺序。无正分时首页直接出官方工具和其余通用动作。“浏览其他操作”始终可从首页进入，输入到齐的所有片段都可按每页 12 项浏览。用户题面提供目标证据，工具返回和模型自己发出的搜索词均不能单独触发推荐。

程序还可从最近 4 个观测拟出通用计算，主菜单剩余位置至多放 4 个。支持真实字段上的计数、求和、平均、唯一极值记录、去重、分组、拼接。字段和操作要与题面、范围、数据类型相符。并列极值保留歧义。选中片段或计算后，输出登记成新观测，再次出下一步题。写操作需另选官方工具。

每个官方工具上的选择说明随该工具进入菜单，交接指导在选定工具且需要局部生成时取用。JevRSI 的公开实现把任务、目标、背包、观测和当前状态拼成查询，用 BM25 排列 procedure，并用元数据词的重合筛选适用范围，默认最多取三条。这里用片段的实际来源和可选目标短语实现按需推荐，Jev 仍决定下一步动作。[JevRSI 检索代码](https://github.com/usail-hkust/JevRSI/blob/825a4e83e6c6805c7b7255d514e62b3668a20a76/jevmaster/skills/retrieval.py#L154) · [procedure 适用范围与数量](https://github.com/usail-hkust/JevRSI/blob/825a4e83e6c6805c7b7255d514e62b3668a20a76/jevmaster/skills/runtime.py#L232)

**第二道题绑定对象和参数。** 依次收集 Sol 安装的绑定程序、可从观察文本构造的单行编辑、同一条公开记录的字段投影、题面字面值及公开默认值。答案提交还可选择标量观测或观测字典的标量字段。按实际参数批次去重、保留第一个来源。字段优先精确对齐名字，例如 `receiver.email → receiver_email`。同时检查实际类型。按名字、标题等限定的子集合以及所有当前记录分别展示，题目可以选择一人、多条记录、整组或弃权。每页最多 12 组参数。相关参数为空或只有一个读取默认值时，调用可直接执行。写操作仍要先在动作题被选中。问答题可绑定 `answer`。已有写回执、且题面未被识别为询问时，已选的完成动作可按官方默认结束。这个判断是题面启发式，复杂的多目标题仍会提前结束。

字面值来自公开原文的引号内容、数字、枚举、名词修饰语与名称。一个槽最多留 5 个值，枚举到 80 个有效组合为止。电话号码和邮箱要具有对应形态。对一个观测的候选范围最多列 8 个匹配子集和一个全范围。整数、布尔值、上下限、枚举、数组元素、必填项、未知参数和跨记录的同一行绑定由执行器检查。

**局部生成后的返回。** 已选定工具而参数选不出来时调用 `G_binding`，它看到当前状态、这个工具的完整签名和本工具的 handoff 提示。连下一步工具都未确定时调用 `G_tool`，它看到当前状态、独立排序的前 12 个公开工具与完成工具。后者的目录不拼入学习片段的说明。纯生成臂每步使用 `G_tool`。下列示例展示模型可以提交的几种结构化动作。

```json
{"tool":"venmo__create_transaction","source":"r2","arguments":{"receiver_email":{"field":"receiver.email"},"amount":{"field":"amount"}}}
{"inspect":{"source":"r2","row":0,"field":"content","offset":500}}
{"calculate":{"source":"r1","op":"argmax","field":"play_count"}}
{"search":"incoming messages about movie recommendations"}
{"source":"r2","arguments":{"note_id":{"field":"note_id"},"content":{"replace_text":{"field":"content","old":"[ ] Pack tent","new":"[x] Pack tent"}}}}
```

这些行是不同请求的例子。一个回复只解析一个 JSON。行选择可带 `where` 精确匹配、`order_by`、`take=first/last`。默认处理全部匹配记录。文本 `inspect` 一次最多看 500 字符，结果记为摘录。开放计算还支持 `project/distinct/group/join`，这里的 `join` 是连接字符串。关联两个数据源可用学习片段的 `inputs`。任一步成功或出错后都可重新进入 Jev 选项。生成的搜索词会参与下一轮检索。自由 Python 仅出现在离线受限片段里。在线环境的 Python 调用壳由程序构造。

**执行与结束。** 登录按公开签名确定用户名类型，向 supervisor 取得与目标应用同名的凭据，一题内复用该应用 access token。认证值在公开轨迹里脱敏。未指定页号或页大小时自动收全，页大小不超过 20 与官方 maximum。只要显式给了其中一个，就只读指定页，另一个采用官方默认。第一页不足页大小时该返回可标完整。相同读取可利用已有观测。成功写入清掉读缓存。批量操作先检查全部参数再逐项执行。同一批次部分成功后以同一参数重试，跳过已成功前缀。HTTP 失败完整计入实际尝试，只为成功返回的那一项写接受事件。最后调用 supervisor 完成并官方评分，或在预算到达时对当前实际世界评分。

## 4. 写操作怎样向 Jev 表示“改了什么”

AppWorld 的 `update_note` 接受只带 `note_id` 的请求，实际正文保持原样也会给出成功消息。本版按公开 `update_*` 工具的签名分清定位字段与待改字段。必须的 `*_id` 或 `*_path` 用于定位。其他非认证、非分页字段可表示实际设定。账号资料更新允许隐含对象“当前账号”。实参至少含一项非 null 待改值。`false`、`0`、空字符串和空列表可表达真实操作。条件用于程序构造的选项及生成的实际调用。关注艺人、删除某条记录等动词本身已表达效果，可以合法只带对象 ID。

Jev 在更新菜单看到对象、批量数量、字段和拟设值。若同应用曾返回这个同标识对象，还可看到最近可用观测中的旧值、与新值是否相同，长文本给出首个不同字符周围的内容。相同设定可满足幂等操作，保留在选项中。回执显示本次请求的修改和官方回答。修改效果需结合公开数据或评分判断。

对已有文本中的 Markdown 复选框，程序扫描真实行，识别 `[ ]`、`[x]`、`[X]`，支持项目符号和缩进。只有当该行项目在本字段内唯一且其文字出现在题面，才为该项构造设值候选。题面明确要求完成或未完成时给出这一设定，原本已满足时保留原值。方向含混时两个设定都交给 Jev 选。Jev 仍决定动作和是否采用这一变更。只改标记字符，其余正文、换行保留。其他文本可在 `G_binding` 中用 `replace_text`，它须在指定来源行中恰好找到一处非空旧串。遇到重复或找不到的旧串，下一步可以读更多内容、换绑定或生成明确的值。同一对象字段经过本次任务自己的成功更新后，依赖其旧观测的这种文本编辑需要重新读取。对完全自由写出的文字，系统掌握的是提交内容，其来源仍需核对。

## 5. 模型与资源账

| 设置 | 值与实际口径 |
|---|---|
| 执行模型 | Jev 判断与开放生成共用固定 27B 骨干。判断使用发布的适配器及官方 `/v1/decide`。开放生成使用同一服务的基础模型 completions |
| 判断输入 | 问题、局部 skill、状态 JSON、最多 16 个含弃权的选项。Jev 输出索引及概率，程序取回对应的真实值 |
| 自适应 | 动作、参数、应用及新增的片段内部记录菜单共用官方 `thinking=auto`。阈值 0.60，低置信最多 256 个推理 token。概率融合使用发布设置 mix=0.5。判断日志同时保存快判、复判和融合结果。在仅余一次模型请求时保留快速判断 |
| 开放输出 | 温度 0，固定 seed 20261119。每次最多 640 个输出 token，受本题剩余预算限制。其中思考最多 256 个，至少留一个位置给答复。输出截断或 JSON 不可执行时记录错误并进入下一步 |
| 单题预算 | 最多 40 个逻辑模型请求、8,192 个在线输出 token、300 次官方 API、900 秒墙钟。一次自适应判断实际用了内部推理时会多占一个逻辑请求。错误尝试可能计入请求。服务上下文上限默认 16,384 |
| 并发 | 每 GPU 两条独立世界、同一模型服务。控制器按题号给设备亲和性，候选优先沿用入口时的设备 |
| 结束与重试 | 正常提交或执行预算耗尽都交给官方 evaluator。业务失败在同一任务状态里反馈给模型。基础设施异常由运行器另开 attempt，单次调度最多两次。启动阶段的设备故障单独处理 |

在 `output_tokens` 中，快速打分时服务的选项读出 token 单列在底层 usage。不要把输出为零解读成零推理成本。时延还受批处理、节点负载、模型服务预热与 AppWorld 调用影响。

复现时可在本地逐题轨迹的 `model.request` 查看发给 27B 的实际输入。动作问题为 `Which NEXT operation is supported by the request and current progress?`，参数问题为 `Which arguments and scope for <tool> match the user's request?`。前者提醒先确认相关来源、动作方向和剩余目标，后者提醒检查对象范围和参数依据。回答索引用于取出程序保留的候选值，模型无需抄长 ID 或全文。协议配置还列有通用执行器的 `history_chars=18000`，本公共工具入口自行按观测、样本与字段裁剪模型视图。

## 6. Sol 可以改什么

库是一个有六个顶层键的 JSON。冷启动六个字典都是空，公共执行程序和官方工具目录仍然存在。以下是一个学习对象进入执行器的准确位置。

| 键 | 命名方式与内容 | 生效时机与边界 |
|---|---|---|
| `retrieval` | 官方工具名 → 短检索说明 | 改变该工具的候选排序。仍须被 Jev 选择 |
| `decision` | 官方工具名 → 短选择指导 | 只附在该工具的菜单项后，解释何时选它 |
| `binding` | 官方工具名 → 主来源、可选辅助来源、说明、纯程序 | 在选择该工具后，把观测转为一项或一批具体 kwargs，进绑定菜单。按真实公开签名检验 |
| `fragment` | 独立名字 → 来源、说明、纯程序、可选目标短语和内部问题模板 | 来源到齐后可浏览，与题面目标匹配时上首页。选中后程序先算，每次遇到需要语义判断的记录都可以请 Jev 选择，最终输出登记为新观测 |
| `state` | 独立名字 → 主来源、说明、纯程序 | 新观测到达时生成紧凑派生证据，随状态呈现，最多展示约 600 字符 |
| `handoff` | 官方工具名 → 局部生成指导 | 选定该工具、绑定需开放生成时，附在该次 `G_binding` 请求里 |

每个补丁最多 **3 个不同的“类别、名字”组合**。同一组合在一个补丁只能写一次。已有对象可改写或以 `value:null` 删除。每份提交相对本轮父库计算。可修改项由这个接口决定。模型权重、公开工具定义、基础检索公式、页宽、模型预算、模拟器和官方评分器都属于固定实验实现。

声明式对象的 `sources` 为一个或多个可替代的主来源，`inputs` 为需要同时观察到的辅助来源。辅助来源只能用于 binding/fragment。程序接收 `instruction, datetime, rows, source, scope, complete, inputs`。`inputs[来源]` 带对应的行、引用、范围和完整性。绑定返回由公开实参组成的列表，片段返回能序列化为 JSON 的观测，state 返回简明证据。输入不足可以返回 `None`。程序体最多 5,000 字符，运行在输入数据的深拷贝上。支持赋值、if、for、列表/字典操作等受限 Python。常用函数包括 `len any all sorted min max sum enumerate zip str int float list dict set isinstance regex captures`。无导入、文件、网络、API 调用权限。模型生成的片段无需包含场景 ID、人名或答案常量。

### 片段内何时继续问 Jev

这是本地执行器对 v2 的扩展。已计分的电影片段使用直接计算。Sol 可以把几个可能遇到的问题定义在同一片段的 `choices` 里，整个片段仍占一个具名修改项。例如，下列片段以已读的短信和笔记目录为输入。

```json
{
  "sources": ["simple_note__search_notes"],
  "inputs": ["phone__search_text_messages"],
  "choices": {
    "message": {
      "source": "phone__search_text_messages", "fields": ["sender.name", "message"],
      "question": "Which incoming message contains the request the user wants answered?"
    },
    "note": {
      "source": "simple_note__search_notes", "fields": ["title", "tags"],
      "question": "Which note's subject and purpose match the referenced request?"
    }
  }
}
```

片段从实际数据初筛。能唯一绑定时程序继续算，证据不足可以返回 `None`。若两条短信都符合结构条件，程序可以返回 `{"$choose":{"role":"message","rows":[4,7]}}`。行号从 0 起算。执行器用数组中指定行的实际字段组装 1 至 15 条记录和一个 `NONE`，每个字段显示最多约 500 字符。Jev 看到本题指令、数据来源、来源完整性和本次选项。搜索词和片段说明保留在其各自使用的环节。

如果 Jev 选中 `r1[7]`，程序带着这条结果重新计算。首次进入用 `state.get("selections", [])` 读取空历史。后续 `state["selections"]` 依次保留各问的 `role, source, ref, row, value`，`state["selected"]` 提供最近选中的完整公开记录及其位置。程序可以直接返回，也可以继续询问，例如 `{"$choose":{"role":"note","rows":[2,5],"using":{"message":7}}}`。此时 Jev 能看到第 7 条短信声明的发件人和正文，只需从两条笔记中选。程序自己定位到短信行时，也能把它作为第二问的依据。每个判断共享整题请求、输出 token 和时间预算。同一个问题可以针对另一条短信再次使用。如果程序再次请求已经回答过的同一问题、同一组候选和同样的依据，这次片段结束，已有答案可从历史读取。选择 `NONE` 时也结束该次片段并回到外层动作选择。实际写入仍需选择官方工具和参数。原先 `choice` 与 `{"$choose":[4,7]}` 的写法继续可用。

完整轨迹保留每次 `native/fragment_choice` 的实际菜单与选择。`internal_choices` 记录判断角色、来源、行号、引用的依据和是否继续提问。离线检查跳过的片段若返回 `$choose`，则报告 `needs_fragment_choice`。历史题在相同问题和选项上沿用旧记录，可以回放到第二问或更后面的首处变化。新插入的问题按已有复选预算送给 27B。若旧决策和新问题承担不同角色，或针对不同的参照行，则另行标明二者的关系。

## 7. 小样本试验的一轮优化

1. **采样。** 用同一初始库运行入口 Jev 臂，并让纯生成臂在另一个重置世界完成同一道题。当前 Train 与检查题均计分。编辑器的入口只索引当前 `--train` 的两个臂，以及显式 `--history-run` 中先前开放的 Train 任务。多个历史目录按命令行顺序读取，最后一个历史候选成为本轮入口。
2. **Sol 接到什么。** 初次输入含完整父库，每条开放轨迹的题面、成败、输出、开放生成次数、按顺序的动作/参数/观测/错误、生成出现的位置与片段使用报告。索引里的步骤最多显示前 70 项。完整轨迹另可按 `doc,start,count,offset` 翻页。每页默认 6 个事件，最多 50 个，序列化文本预算 16,000 字符，长事件有续读游标。可查 `tools` 获得官方签名。条目名字区分 `h0_generation/<id>`、`h0_decision/<id>`、`history0/candidate/<id>` 等。
3. **Sol 诊断并提交草案。** GPT-6.2 Sol、reasoning effort=max、当前 Codex 账号，编辑器在只读会话运行，工具和 shell 关闭。最多 8 次首阶段回复，前 7 次可以申请证据页，总次数包含无效 JSON 或不合规范的补丁，第 8 次须给出完整补丁。最短形式为 `{"reason":"依据和预计影响","objects":[{"kind":"decision","name":"公开工具名","value":"短说明"}]}`。可有依据地提交空对象数组。程序把补丁实际施加到父库，检查对象、来源、程序语法与可执行性。
4. **免费回放与实模复选。** 在记录的相同状态上，将草案重新编译。逐次匹配公开 API、模型输入、菜单及所绑定的真实选项。一路相同就用原记录继续。首处新菜单不能借用旧索引，程序记录旧选择并把真实新菜单交给 27B。当前批合计最多实选一个变化点。每道曾做对的历史 Train 在自己的首处变化处检查，合计最多 24 次真实复选，其余标记等待实选。相同/不同语义、相同显示文字分开记。两种计算口径不同而碰巧挑中同一条记录时还可报告局部输出相同。变化首先出现在开放生成或 API 时报告该边界。这里衡量首处分歧，对整题是否保住以整题结果为准。
5. **新增的一道整题草案实跑。** 补丁改变了库，而且在当前优化题上观察到相关来源或实际请求变化时，至多选 **1 道当前 Train** 从初始环境执行整个草案。选题按被改对象的相关来源/工具命中数、是否出现请求变化、入口是否失败、原题单顺序依次排序。检查题、旧题均不会成为这道探针。它享有普通单题的相同预算，在 `runs/draft_train_XX/` 单独记录。相同草案与同一题的有效已存结果可以在中断续跑时复用。
6. **Sol 审阅。** Sol 会同时收到草案、当前首处分歧、所有开放的旧成功题的首处检查、整题草案的成败/成本、真实提交和片段使用报告。它还可为审阅单独申请 **1 页** 完整证据（包括 `draft/<id>` 的原始轨迹），随后给出最终补丁。通常一条审阅回复，需要翻页时两条。审阅返回非法补丁，保留上一个可应用草案并写明原因。首阶段用尽机会仍无有效草案则报错。若初次提交与父库一致，跳过多余预览与审阅。
7. **候选新跑。** 将最后实际使用的完整库写入 `offline/candidate.json`，在所有当前 Train 和检查题上各重置一次环境、重新计分，包括已跑过草案的那一道。这样可以比较新版本，而不会把 Sol 在审阅时已经看到的草案分数拿来充当候选分数。审阅若再次改草案，只有这一次候选运行能证明最终库的实测效果。结果与片段报告供后续显式开放这批 Train 时使用。单次 `all` 只演化一轮，更多轮由新的根目录和 `--history-run` 明确衔接。

按本轮的三道优化、三道检查，常规计分为 6 × 3 个 episode，草案预览额外至多 1 个 episode。首处复选只执行一个判断请求。历史预览不会重跑整道旧题。一次正常编辑的 Sol 回复上限为 8 + 2，计数和 token 以每次 `usage.json` 为准。技能提示会影响选择概率，Sol 也可能提出过窄的语言规则。采用过一个候选或一个历史先例，都不构成跨场景成功的保证。

## 8. 怎样判读片段使用证据

每个计分 episode 有自己的 `fragment_flow.json`。编辑器在草案审阅和下一轮历史读取中使用同一计算逻辑。可以从某个片段名字逐项跟进。

时间点会影响结论。`draft_preview.json` 描述送审的草案。审阅后再改过的最终库，要看候选整题轨迹。历史试跑结束后，用最终库回放了两道已开放的历史成功题，退款与关注艺人的 10 和 8 个请求分别全程一致。这项核对是在 Sol 提交最终补丁后完成的。

| 记录 | 回答的问题 |
|---|---|
| `eligible` / `recommended` / `offered` | 来源到齐后可执行多少次？其中多少次被推荐到动作页？包括主动浏览在内，Jev 实际看到了几次？同题反复呈现会重复计数 |
| `chosen` / `produced` | Jev 选过几次？程序跑后产生哪个 `rN`、几行？选择后返回空也有记录可区分 |
| `accepted_uses` | 哪个已由 AppWorld 接受的写入/提交接到了该观测？列实际端点、事件位置、输入与输出引用 |
| `role` | 直接把观测字段投影到哪一个参数。只以观测限制行范围。是某个绑定程序的输入。或先经过其他观测/计算再进入调用。后几种能证明依赖关系的范围各不相同 |
| `bypassed_for` | 片段出现在菜单时，Jev 实际选了哪个动作？摘要保留前 6 个例子 |
| `skipped_output_checks` | 在可见但跳过片段后若发生接受的写入或提交，离线在当时的公开观测上运行那个纯片段，将同名字段与提交实参比较。最多展示前 6 个例子。可用来发现“片段算出两个标题，实际发了八个” |
| `last_accepted_operations` | 全部成功接受操作的次数和最后 5 项摘要，方便即使官方判对也能抽查正文、对象或答案 |

程序记录明确的来源与绑定方式。模型自行写出的字面量即使与片段结果相同，也不能自动计作直接使用。程序收到了某来源不代表其每个输出字段都由该来源决定。跳过后补算的片段不产生新的线上调用，也不计作片段使用。输出与已提交实参不同时，还需回到题面和原始回显判断谁符合要求。旧 v1 日志可以恢复当时的菜单、选择、返回数据和实际写入，缺失的显式来源标为旧格式。所有这些诊断都在公开 Train 轨迹上完成。

| `runs/<stage>/<task>/record.json` | 官方分数、token、API、耗时、GPU 和实际 trace 路径。每条计分记录计一次 |
| `runs/<stage>/<task>/attempt_N/trace.jsonl` | 逐条查看编译的菜单、索引、实参、公开返回、实际接受效果和预算。低置信判断有 `step_review` |
| `runs/<stage>/<task>/fragment_flow.json` | 三个计分臂的片段使用报告 |
| `offline/public_functions.json` | 运行时取回的公开工具定义 |
| `offline/sol/system.txt`、`offline/sol/*/{request.txt,response.txt,usage.json}` | 本次 Sol 完整系统提示、每次实际用户输入、回复与成本 |
| `offline/proposal.json`、`offline/candidate.json` | 最终增量及施加后的完整库 |
| `offline/draft_trials/`、`offline/draft_preview.json` | 实测的草案身份（题目与完整库）、首处复选、历史影响、整题预览和片段证据 |
| `pilot_results.json` | 三臂并排结果。内部草案计费需从独立场次读取 |

汇总示例，可直接在已完成任一命令的机器上运行。换成自己的目录即可。

```bash
python - runs/v2-evolve/pilot_results.json <<'PY'
import json, sys
rows = json.load(open(sys.argv[1], encoding="utf-8"))
for group in ("optimization", "withheld Train"):
    for arm in ("h0_generation", "h0_decision", "candidate"):
        part = [r for r in rows if r["stage"] == arm and r["panel"] == group]
        print(group, arm, sum(r["success"] for r in part), "/", len(part),
              "output", sum(r["output_tokens"] for r in part),
              "open calls", sum(r["open_calls"] for r in part))
PY
```

## 10. 实际走一遍电影短信训练题

题面要求回复 Christopher 的电影推荐短信，并且片名要来自自己的 Simple Note。题面没有写出导演。来信中指定的是 David Fincher，公开笔记中对应的两部是 *Fight Club* 与 *The Social Network*。这一步既需要读另一应用中的约束，又需要从笔记筛选，最后还要把同一个来信人的号码和筛选结果一起交给发送工具。

1. 本轮入口已经继承了 `note_titles_for_sms_director`。入口 Jev 读到短信与笔记之后，片段在实际菜单出现 3 次，选择 0 次。最终号码正确，短信却写了 7 部无关电影，遗漏了那两部。纯生成臂在独立世界发对了两部。Sol 首次输入中能看到这项分歧、实际短信、离线片段返回与完整证据的索引。
2. Sol 翻看两臂轨迹，第一次提交两个 decision 改动，分别指导何时发送短信和何时重读单条短信。首处变化的菜单交给真实 27B 后，修改前后都选择搜索短信。该次复选用了 441 个输入 token 和 0 个输出 token。另两道当前优化题以及两道曾做对的历史 Train 的首处检查均没有出现新的请求。
3. 在草案的完整独立实跑中，模型读了来信、搜索了笔记，只得到标题和 ID，跳过了读取笔记正文这一步。完整来源未到齐，学习片段没有进入菜单。模型随后发送 6 部，其中 4 部不在笔记的目标集合内。官方判通过，花费 1,652 个输出和 5 次开放生成。报告保留这次官方通过和实际内容差异。Sol 审阅时额外打开了草案从事件 39 开始的一页完整轨迹。
4. Sol 根据这次运行换了一份补丁。它提高了 `simple_note__show_note` 在需要笔记正文时的检索相关性，给同一工具添加“搜索结果只有标题和 ID，需要读正文”的选择说明，并改写 `phone__send_text_message` 的选择说明，要求收件人与发送内容都有来源再发送。原草案用在短信重读上的编辑位被腾出。最终一项 retrieval、两项 decision，共三个具名对象。原片段程序沿用父版。
5. 最终候选重新从空世界执行。它实际取得短信与笔记正文，片段出现在菜单一次，Jev 选中一次，程序返回 `r4`。发送时程序从 `r4.message` 绑定正文，从同一行的 `r4.phone_number` 绑定收件人。两部电影均符合笔记，只有一次被接受的发送。整题耗费 1,824 个输出、3 次开放生成，官方通过。
6. 留出的 Laura 题有另一位联系人、另一位导演 Quentin Tarantino 和另一组笔记。沿用同一候选，片段同样出现一次、被选一次、产生 `r4`，两个字段都进入被接受的短信。内容恰为 *Django Unchained, Pulp Fiction*。这是新实例上的真实复用。另做控制，将每题实际交给片段的两份公开观测固定，只把题面开头改为“Read …'s incoming text message…”。两个原题运行片段都能得到准确标题，两个改写都返回空。这是片段程序对措辞的单独测试，整题的回退或补救能力在该项控制中没有采样。

分开读优化与检查更容易看清收益。在 3 道优化题上，入口与候选是 2/3、2,897 输出和 3/3、1,824 输出。在 3 道检查上，则是 1/3、5,840 输出和 2/3、4,293 输出。两道清单题实际均只改变目标行，Jev 两版各一次更新、零开放生成。此收益归于工程实现的公共编辑选项。两道电影题归于有实际使用证据的 Sol 修改，题目对应的片段早已存在。

全部六题上，候选比父库少 30.0% 总输出，开放生成次数却由 13 增至 19。完全不同的 Venmo 题占了主要差异。父库和候选都先把已收到的实际付款理解为收到的付款请求，后来均用完 40 次逻辑模型请求，均没有成功执行所需的点赞或评论。候选在这题调了 13 次开放生成，父库为 6 次。把父版记录的整条路径放在最终库上，可以对齐全部 39 个已记录请求。两次实跑的首次生成请求与种子一致，回答的最终 JSON 也相同。第 3 次开放生成时，同一请求分别写出了较长与较短的同事搜索词，后续路径才在结构化动作上分开。不能仅凭这道题较少的总输出就认为跨场景问题已解决。

Sol 此轮 10 次回复合计 11,573 个离线输出 token，账户回复耗时合计约 286 秒。整题草案实跑另耗约 74 秒。没有使用正式 Dev/Test。起初自动选中的另一节点在 Numba 缓存初始化时失败，该节点没有产生任何题目成绩，上表全来自两张 node15 A800。完成后对文本目标已满足时应当幂等的情况补了普通回归测试，并用最终代码重放 18 条计分轨迹和 1 条草案轨迹，19 条均匹配全部记录请求。

本地复现后，可从 `pilot_results.json` 重算分组成本。逐题 `trace.jsonl` 保留实际提交的 API 参数，`fragment_flow.json` 保留片段对这些参数的贡献。Sol 的提示词和回复保存在本次运行的 `offline/sol/`。
